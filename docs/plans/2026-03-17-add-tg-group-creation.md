# План: добавить создание Telegram-групп в MCP

## Цель

Добавить в MCP новый tool для создания обычной приватной Telegram-группы с минимальным API: один обязательный параметр `title` и короткий стабильный ответ с полями `status`, `chat_id`, `title`.

## Не-цель

- не добавлять участников при создании;
- не создавать supergroup или channel;
- не настраивать username, invite link, avatar, права или описание;
- не вводить отдельные safety-ограничения вроде `confirm=true` или whitelist для этого MVP;
- не делать расширенный ответ с большим количеством Telegram-метаданных.

## Предпосылки и ограничения

- Проект уже использует паттерн `server.py -> TelegramBridge` для MCP tools.
- Write-операции обычно проходят через тонкую обертку в `tg_mcp/server.py` и основную Telegram-логику в `tg_mcp/telegram_client.py`.
- Для MVP нужен только `tg_create_group(title)`.
- Группа создается от имени авторизованного пользовательского Telegram-аккаунта, сохраненного в `TG_SESSION_PATH`, а не от имени бота.
- Локальная валидация должна быть минимальной: отклонять пустой или пробельный `title`, остальные ошибки делегировать Telegram API.
- Тестирование должно включать unit и e2e с реальным Telegram.
- Из-за отсутствия safety-флага tool будет более “мощным”, чем текущие write-tools; это осознанное решение и его надо явно задокументировать.
- Финальная сигнатура MVP: `tg_create_group(title)` без `chat`, `confirm` и дополнительных параметров.

## Подход

Добавить новый MCP tool `tg_create_group(title)` в `tg_mcp/server.py`, реализовать создание обычной приватной группы в `TelegramBridge` через совместимый с текущей версией Telethon API, вернуть минимальный payload `status`, `chat_id`, `title`, покрыть unit-тестами и добавить отдельный e2e smoke-сценарий с реальным Telegram-аккаунтом.

## Тест-план

### Unit

- Успешное создание группы возвращает минимальный payload с ключами `status`, `chat_id`, `title`.
- Пустой `title` вызывает `ValueError` с понятным текстом ошибки.
- `title` из одних пробелов вызывает `ValueError`.
- Слишком длинный `title` не ломает локальную логику; фактический результат Telegram API зафиксирован тестом или документацией.
- Ошибка Telethon API не теряется и доходит до caller в предсказуемом виде.
- Server tool вызывает `bridge.create_group(title)` и оборачивает результат в `{"status": "ok", ...}`.

### Integration

- Не требуется отдельный integration-слой сверх текущих unit-тестов, если bridge уже мокается на границе Telethon.

### E2E

- Отдельный real-Telegram smoke-test создает временную тестовую группу через живую сессию.
- Тест проверяет, что группа реально создана и ответ содержит минимум `status` и идентификатор/название сущности.
- E2E должен запускаться только вручную или под явным флагом окружения, например `TG_RUN_REAL_E2E=1`.
- E2E должен иметь явную skip/mark-логику, чтобы не попадать в обычный CI-прогон.
- После E2E должен быть понятен cleanup test-артефакта: удаление, архивирование или ручная уборка по соглашению.

### Негативные кейсы

- `title=""`
- `title="   "`
- слишком длинный `title`
- Telegram API отклоняет создание группы
- нет авторизованной Telegram-сессии

## Риски и откаты

- Основной риск: неверно выбрать Telethon API и случайно создать не тот тип сущности (например, channel/supergroup вместо обычной группы).
- Основной риск: отсутствие `confirm` делает tool более опасным для случайного вызова, чем другие write-tools.
- Основной риск: ограничения Telegram API могут проявиться как `FloodWait` или другие runtime-ошибки уже на реальном аккаунте.
- Основной риск: real-Telegram e2e может оставлять тестовые группы, если не продумать ручную очистку.
- Откат простой: удалить tool из `tg_mcp/server.py`, удалить bridge-метод, убрать документацию и тесты.
- Если после релиза выяснится, что отсутствие safety-ограничений слишком рискованно, следующий шаг отката/смягчения - добавить `confirm=true` без расширения функциональности.
