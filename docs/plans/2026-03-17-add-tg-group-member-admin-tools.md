# План: добавить tools для управления членами Telegram-группы

## Цель

Добавить в MCP два tool для редактирования списка участников Telegram-группы: добавление участника и удаление участника, с обязательной защитой через `confirm=true` и отдельный whitelist групп на администрирование.

## Не-цель

- не добавлять ban/unban как отдельные инструменты;
- не добавлять promote/demote, роли, mute, права администратора;
- не поддерживать массовое добавление или массовое удаление участников в MVP;
- не использовать `TG_DEFAULT_CHAT` для admin-операций;
- не переиспользовать `TG_WRITE_CHAT_WHITELIST` вместо отдельного admin-whitelist;
- не делать расширенный UI/flow для подтверждения beyond `confirm=true`.

## Предпосылки и ограничения

- Проект уже использует паттерн `config -> server guard -> TelegramBridge`.
- Точка входа для новых tools - `tg_mcp/server.py`, конфиг - `tg_mcp/config.py`, Telegram API-логика - `tg_mcp/telegram_client.py`.
- Для MVP нужны два инструмента: условно `tg_add_group_member(chat, member, confirm=false)` и `tg_remove_group_member(chat, member, confirm=false)`.
- Параметр `chat` должен быть обязательным и явным для каждого вызова.
- Параметр `member` должен принимать `@username` или numeric id строкой.
- Admin-операции должны быть разрешены только для групп из отдельного env whitelist: `TG_ADMIN_CHAT_WHITELIST`.
- Помимо whitelist нужен `confirm=true` по аналогии с существующими write-tools.
- Удаление участника семантически означает remove/kick, а не отдельный ban-tool; если выбранный Telegram API требует внутренний ban/unban, это остается внутренней деталью реализации.
- MVP должен явно поддерживать только те типы чатов, для которых выбранный Telethon API стабильно работает; неподдерживаемые типы должны возвращать понятную ошибку `unsupported_chat_type`.
- Новый `TG_ADMIN_CHAT_WHITELIST` не должен ломать текущие env и существующие tools.
- Тестирование должно включать unit, e2e-style на заглушках и отдельный live Telegram smoke.

## Подход

Добавить новый конфиг `TG_ADMIN_CHAT_WHITELIST`, реализовать в `server.py` отдельную проверку admin-доступа для заданного `chat`, затем добавить в `TelegramBridge` минимальные методы для добавления и удаления участника по `member`, используя совместимый с текущей версией Telethon API только для поддерживаемых типов чатов. Снаружи tools остаются простыми и безопасными: явный `chat`, явный `member`, `confirm=true`, короткий стабильный ответ. Минимальный ответ каждого tool: `status`, `chat`, `member`, `action`.

## Тест-план

### Unit

- Загрузка `TG_ADMIN_CHAT_WHITELIST` корректно парсит список значений.
- Tool отклоняет вызов без `confirm=true`.
- Tool отклоняет вызов при пустом `TG_ADMIN_CHAT_WHITELIST`.
- Tool отклоняет вызов, если `chat` не входит в `TG_ADMIN_CHAT_WHITELIST`.
- Tool отклоняет пустой `chat`.
- Tool отклоняет пустой `member`.
- Bridge корректно обрабатывает `member` в виде `@username`.
- Bridge корректно обрабатывает `member` в виде numeric id.
- Bridge возвращает понятную ошибку для неподдерживаемого типа чата.
- `member` уже состоит в группе обрабатывается предсказуемо и документированно.
- `member` не найден обрабатывается предсказуемо и документированно.
- `member` уже отсутствует в группе обрабатывается предсказуемо и документированно.
- Ошибки Telegram API не теряются и доходят до caller в предсказуемом виде.

### Integration / e2e-style

- Server tools корректно вызывают bridge-методы с ожидаемыми аргументами.
- Ответ tools соответствует зафиксированному контракту.
- Заглушки покрывают happy path и key negative path без живого Telegram.

### Live E2E

- Отдельный manual smoke-test запускается только под `TG_RUN_REAL_E2E=1`.
- Тест проверяет, что участник может быть добавлен в whitelisted group.
- Тест проверяет, что участник может быть удален из той же группы.
- Для live e2e должна быть заранее подготовлена отдельная тестовая группа, входящая в `TG_ADMIN_CHAT_WHITELIST`.
- Для live e2e должен быть заранее известен отдельный тестовый пользователь/аккаунт для add/remove операции, не боевой.
- После live e2e должно быть понятно, как вернуть тестовую группу и тестового участника в исходное состояние.

### Негативные кейсы

- `chat=""`
- `member=""`
- `confirm=false`
- пустой `TG_ADMIN_CHAT_WHITELIST`
- `chat` отсутствует в `TG_ADMIN_CHAT_WHITELIST`
- чат имеет неподдерживаемый тип
- `member` уже состоит в группе
- `member` не найден
- `member` уже отсутствует в группе
- Telegram API отклоняет добавление участника
- Telegram API отклоняет удаление участника
- нет прав администратора у текущей Telegram-сессии в целевой группе

## Риски и откаты

- Основной риск: Telethon/Telegram API по-разному ведет себя для обычных групп, supergroup и каналов; в MVP важно не обещать лишнюю универсальность.
- Основной риск: remove может технически требовать ban/unban внутри API, и это нужно проверить до реализации.
- Основной риск: live e2e зависит от реальной test group и тестового участника, что делает прогон более хрупким.
- Основной риск: неверная настройка `TG_ADMIN_CHAT_WHITELIST` может либо заблокировать нужный сценарий, либо случайно открыть админские операции не там.
- Откат простой: удалить новые tools из `tg_mcp/server.py`, убрать `admin_chat_whitelist` из `tg_mcp/config.py`, удалить bridge-методы, документацию и тесты.
- Если окажется, что add/remove слишком различаются между типами чатов, следующий безопасный откат/смягчение - явно ограничить поддержку только обычными группами или только одним типом сущности с понятной ошибкой.
